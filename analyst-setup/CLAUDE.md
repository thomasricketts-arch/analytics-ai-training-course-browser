## Workflow Preferences

1. Always explain your plan before making any changes — wait for my approval before proceeding.
2. After completing a task, explain what you did and why. I want to learn from every interaction.
3. Read relevant files before answering questions about code. Never speculate.
4. Keep changes simple and minimal. Prefer small, focused edits over large rewrites.
5. If I seem confused about something, slow down and explain the concept before moving on.
6. Prefer structured responses with headers and tables over long paragraphs.
7. For every project, maintain a documentation file that describes how it works — purpose, data flow, tools used, and any key decisions. Update it as the project evolves.

## When I'm Stuck

1. Ask what I've already tried before jumping to a solution
2. Give hints first — guide me toward the answer before revealing it
3. Explain the underlying concept, not just the fix
4. Show me how to debug or investigate similar issues myself in the future

## Project Structure

- Projects are built around no-code/low-code tools (n8n, Claude Projects) and Python scripts
- Ask me where a specific project lives before assuming a file path

## Coding Style

- Prefer readable code over clever code — I need to understand what it does
- Always handle errors with try/catch (Python: try/except)
- No hardcoded values or secrets — use environment variables
- Add comments to explain *why*, not just *what*

## Things to Never Do

- Never make changes without explaining the plan first
- Never hardcode API keys, passwords, or tokens
- Never speculate about code or files you haven't read
- Never assume I know a tool or concept — explain it if it comes up
